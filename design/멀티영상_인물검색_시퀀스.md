# 멀티 영상 인물 검색 서비스 설계 초안

이 문서는 영상 사전분석, Intel Re-ID 검색, 사용자 확인 후 후속 검색을 연결한 서비스 설계안이다. 현재 단일 영상 벤치마크 코드에 모두 구현된 기능을 뜻하지 않는다. 아래의 권장 사항은 제안이며, 미정 항목은 팀에서 결정한다.

## 먼저 정리할 용어

- **트랙 ID**: 하나의 영상에서 추적기가 연결한 사람의 등장 구간 번호. `영상 ID + 분석 실행 ID + 트랙 ID`로 구분한다. 서로 다른 영상의 같은 숫자가 같은 사람을 뜻하지 않으며, 같은 사람도 추적이 끊기면 여러 ID가 될 수 있다.
- **대표 사진과 대표 벡터**: 트랙에서 선택한 사람 크롭과 그 사진을 인코딩한 특징 벡터. 어떤 ID를 저장할지 고르기보다는 모든 유효 트랙을 저장하고 각 트랙의 대표 자료를 선택하는 방식이 기본 제안이다.
- **확인된 인물 연결**: 사용자가 동일인으로 확인한 트랙의 연결 기록. 여러 영상의 트랙을 전역 인물 ID로 묶는 기능은 별도 설계·검증이 필요하다.

## 1 영상 사전분석 시퀀스

1. 사용자가 여러 영상을 등록한다. 영상마다 카메라, 촬영 시작 시각, 영상 길이와 접근 권한 범위를 함께 기록한다.
2. 백엔드가 분석 작업을 만들고 영상별 상태를 `대기 → 분석 중 → 완료 / 실패`로 관리한다.
3. 분석 작업자가 YOLO로 사람을 검출하고 추적기로 영상 안의 트랙 ID를 생성한다. 분석 프레임 간격과 추적기는 결정해야 한다. 기존 벤치마크의 1초 간격 사진 검색만으로 전체 추적 데이터가 생기는 것은 아니다.
4. 각 트랙의 프레임 번호, 영상 내 시간, 박스 좌표, 검출 신뢰도, 시작·종료 시점을 기록한다. 상세 기록의 저장 간격은 별도 결정한다.
5. 트랙마다 대표 사람 사진을 고른다. 권장 기준은 충분한 사람 크기, 선명도, 검출 신뢰도이며, 심한 가림과 다른 사람의 혼입을 줄인다. 대표 사진을 여러 장 쓰면 시간과 모습이 다른 후보를 고려한다.
6. Intel Re-ID로 대표 사진의 256차원 벡터를 추출하고 L2 정규화한다. 사진 경로와 벡터를 같은 트랙·대표 사진 레코드에 연결한다.
7. PostgreSQL과 파일 저장소에 자료를 분리해 저장한 뒤 분석 완료 상태를 반영한다.

### 분석 중 사용자 화면 제안

사용자는 분석이 끝날 때까지 화면에 머무를 필요가 없다. 작업은 서버에서 계속 실행하고, 영상별 상태와 `완료 영상 수 / 전체 영상 수`를 보여준다. 실패한 영상은 재시도할 수 있게 한다. 처리시간을 추정할 근거가 생긴 뒤 예상 완료시간을 제공한다.

첫 구현에서는 **선택한 검색 범위의 영상 분석이 모두 완료된 후 검색을 허용**하는 방식이 이해하기 쉽다. 완료된 일부 영상만 먼저 검색하게 할 경우에는 미분석 영상과 누락 가능성을 분명히 표시한다. 완료 알림 방식은 화면 내 상태 표시 또는 앱 내 알림 중에서 결정한다.

## 2 멀티 영상 Re-ID 검색 시퀀스

1. 사용자가 기준 사진과 시간, 검색할 카메라·영상 범위를 입력한다. 여기서 시간이 마지막 목격 시각인지 검색 시작·종료 구간인지는 결정해야 한다.
2. 검색 API가 Intel Re-ID 작업자에게 사진을 전달한다. 현재 검증한 OpenVINO CPU 구성을 우선 제안하며, 실행 위치는 백엔드 서버 또는 분석 서버의 CPU일 수 있다. GPU 서버를 사용하더라도 Intel 모델을 반드시 GPU에서 실행한다는 뜻은 아니다.
3. 사전분석 때와 **같은 Intel 모델·전처리·정규화**로 검색 사진의 256차원 벡터를 만든다. 모델 버전과 전처리 버전도 함께 기록한다.
4. 사용자 초안대로 검색 요청 ID와 기준 사진의 벡터를 PostgreSQL에 저장하고, 입력 사진의 파일 경로를 연결한다. 재검색과 기록 재현에 사용할 수 있으며 입력 사진과 검색 벡터의 보관기간은 결정해야 한다. 검색 기능 자체에 영구 보관이 필수인 것은 아니다.
5. DB에서 접근 권한, 카메라, 시간 조건에 맞는 후보를 좁힌다. 영상별 상대 시간은 촬영 시작 시각을 기준으로 실제 촬영시각에 대응시킨다. 검색 구간과 겹치는 트랙도 포함하며 트랙 시작시각만으로 후보를 제외하지 않는다.
6. PostgreSQL의 pgvector로 대표 벡터와 검색 벡터의 코사인 거리를 비교한다. 대표 사진이 여러 장이면 **트랙별 점수를 집계한 후** 상위 5개 트랙을 선정한다. 집계 방식과 트랙당 대표 사진 수는 결정해야 한다.
7. 후보마다 대표 사진, 카메라·영상, 해당 사진의 촬영시각, 트랙 시작·종료 시각, 유사도를 제공한다. 유사도는 동일인 확률이 아니며, 다른 트랙이 같은 실제 사람일 수도 있다.

Intel 모델의 입력은 BGR, 높이 256 × 너비 128이고 출력은 256차원 벡터다. [Intel 공식 모델 문서](https://docs.openvino.ai/2023.3/omz_models_model_person_reidentification_retail_0287.html)

pgvector는 PostgreSQL에서 벡터 저장과 코사인 거리 검색을 지원한다. 작은 초기 데이터에서는 정확 검색을 기준으로 검증하고, 규모가 커지면 인덱스 방식과 시간 필터 이후 검색 품질을 함께 검토한다. [pgvector 공식 문서](https://github.com/pgvector/pgvector)

## 3 사용자 확인과 후속 검색 시퀀스

### 일치하는 후보를 선택한 경우

1. 사용자가 후보 사진의 **맞음** 버튼을 누른다.
2. 선택한 영상·트랙과 확인 결과를 검색 세션에 기록한다. 확인 전에는 다른 영상의 ID와 자동으로 같은 사람이라고 확정하지 않는다.
3. 선택한 트랙의 마지막 등장 시각 `t_last`를 가져온다. 다른 영상과 비교할 때는 실제 촬영시각으로 변환한다.
4. 해당 원본 영상에서 `[t_last - 5초, t_last + 5초]` 구간을 제공한다. 파일 시작·끝을 벗어나는 범위는 잘라내므로 실제 길이는 10초보다 짧을 수 있다. 원본 보관 영상은 수정하지 않는다.
5. 사용자가 영상을 보고 트랙 끝에서도 같은 사람인지 확인할 수 있게 한다. 대표 사진이 맞았다는 판정만으로 트랙 전체에 ID 전환이 없었다고 보장되지는 않는다.
6. 검색 기준 시각을 마지막 확인 시점 이후로 이동해 다른 영상·카메라를 다시 검색한다. 이미 확인한 구간·기각한 후보는 세션에서 관리해 같은 결과가 계속 반복되는 것을 줄인다.
7. 다음 검색의 사진은 기존 기준 사진을 유지할지, 사용자가 확인한 새 사진을 추가할지 결정한다. 미확인 후보를 자동으로 새 기준 사진으로 사용하는 방식은 피한다.

### 일치하지 않거나 후보가 없는 경우

- **틀림**: 해당 후보를 기각하고 다음 후보를 보여준다. 같은 요청에서의 기각을 영구적인 인물 불일치로 해석하지 않는다.
- **다섯 개 모두 아님**: 다음 후보 묶음을 보거나 시간·카메라 범위, 기준 사진을 조정한다.
- **후보 없음**: 분석 미완료, 해당 시간대에 검출 없음, 유사도 기준 미달을 구분해서 표시한다. 유사도 임계값 도입 여부는 검증 후 결정한다.
- **더 이상 찾지 않음**: 검색을 종료하고 사용자 확인 이력을 남긴다.

## 4 저장 구조 제안

| 데이터 | 저장 위치 제안 | 최소 연결 정보 |
|---|---|---|
| 원본 영상 | 파일 또는 객체 저장소 | 영상 ID, 경로, 카메라 ID, 촬영 시작시각, 길이 |
| 전체 추적 메타데이터 | PostgreSQL, 대량이면 별도 상세 파일과 DB 요약 병행 검토 | 분석 ID, 영상 ID, 트랙 ID, 프레임·시간, 박스, 신뢰도 |
| 트랙별 대표 사람 사진 | 파일 또는 객체 저장소 | 대표 사진 ID, 트랙 키, 프레임·시간, 파일 경로 |
| 대표 사진별 특징 벡터 | PostgreSQL + pgvector | 대표 사진 ID, 트랙 키, 256차원 벡터, 모델·전처리 버전 |
| 검색 요청과 사용자 확인 기록 | PostgreSQL | 세션 ID, 검색 시간·범위, 후보, 판정, 다음 검색 기준시각 |
| 사용자 검색 사진과 벡터 | 사진은 파일 저장소, 벡터는 PostgreSQL + pgvector | 요청 ID, 파일 경로, 벡터, 만료시각 |
| 추적 박스를 그린 영상 | 필요할 때 만드는 선택적 결과 파일 | 원본 영상 ID, 분석 설정·실행 ID |
| 앞뒤 5초 재생 클립 | 원본에서 요청 시 생성·제공, 필요하면 임시 캐시 | 원본 영상 ID, 시작·종료시각, 만료정책 |

대표 사진과 벡터를 모두 저장하되 DB에는 사진 파일 자체 대신 경로를 기록하는 구성을 우선 제안한다. 추적 영상은 디버깅용으로 선택 저장하고, 사용자 확인은 원본 영상으로 제공하는 방향이다. 로컬 디스크·공유 저장소·객체 저장소 중 실제 제품과 장비는 예산·용량·동시 사용자 수를 보고 결정한다.

## 5 결정해야 할 항목

| 결정 항목 | 선택하거나 확인할 내용 | 우선 검토안 |
|---|---|---|
| 사전분석 실행 위치 | 캡스톤실 PC, GPU 서버, 역할 분리 | YOLO는 GPU 분석 작업자, Intel은 CPU 작업자 |
| 검색 Intel 실행 위치 | 백엔드 CPU, 분석 서버 CPU, 별도 서비스 | 초기에는 백엔드 CPU에서 처리 |
| 영상 시각 기준 | 입력 시간의 의미, 카메라 시계 오차, 촬영 시작시각 | 실제 촬영시각과 영상 내 시간을 함께 저장 |
| 추적 방법과 간격 | 추적기 종류, 검출·추적 주기, ID 끊김 처리 | 사진 검색 벤치마크와 별도로 검증 |
| 대표 사진 선정 | 선명도·크기·신뢰도, 가림 처리, 사진 수 | 트랙별 품질 좋은 사진과 그 벡터를 연결 저장 |
| 대표 벡터 정책 | 사진당 벡터, 트랙 평균 벡터, 복수 벡터 점수 집계 | 사진별 벡터를 보존하고 트랙별 집계 방식 검증 |
| 추적 상세 저장량 | 전체 프레임, 일정 간격, 요약·상세 분리 | 트랙 시작·종료와 대표 사진 원본 시점은 필수 |
| 파일 저장소 | 용량, 업로드·재생 속도, 백업, 접근 권한 | 원본과 대표 사진 저장소를 DB와 분리 |
| 분석 중 화면 | 전체 완료 후 검색, 일부 완료부터 검색, 완료 알림 | 상태·진행률 표시, 범위 전체 완료 후 검색 |
| 검색 후보 정책 | 트랙당 결과 수, 사진별 점수 집계, 다음 후보, 임계값 | 중복 트랙 제거 후 Top 5, 기각과 더 보기 제공 |
| 확인 후 재검색 | 원본 사진 유지, 확인된 사진 추가, 다음 시간 범위 | 확인한 마지막 시점 이후 검색, 기준 사진 변경은 사용자 확인 |
| 보관과 재분석 | 원본·사진·벡터 보관기간, 삭제, 모델 변경 시 재추출 | 모델·전처리·분석 버전 기록, 서로 다른 모델 벡터 혼용 금지 |

현재 우선 결정할 세 가지는 **분석을 실행할 장비**, **시간 입력의 의미와 영상 시각 정렬**, **트랙당 대표 사진·벡터 저장 정책**이다. 이 세 항목이 정해지면 저장 용량과 작업 처리시간을 실제 영상으로 산정할 수 있다.
